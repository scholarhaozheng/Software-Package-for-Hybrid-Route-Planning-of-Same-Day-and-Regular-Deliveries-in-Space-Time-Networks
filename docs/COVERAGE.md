# Implementation and specification coverage

The table maps the 29 C# source files to the algorithm specification. It covers data, initialization, optimization, dynamic updates and reporting. The [technical notes](TECHNICAL_NOTES.md) explain implementation differences and solve conditions.

| Component | Implementation | Specification |
| --- | --- | --- |
| Orders, vehicles, spatial and temporal states | `Point.cs`, `Arc.cs`, ten ID/state wrappers in `ClassName/`, and two comparer classes define the records. `RoadNetworkDy.cs` is a placeholder. | Stable identities and support keys; complete package-route and physical-vehicle ownership. [Data structures](../pseudocode/DataStructures.pseudo) |
| Case inputs and epoch demand | `Program.cs` contains parsers and a service-flag reader. Project and case-data files are not included with the C# sources. | Consistent IDs, capacities, duty limits, vehicle modes and order-arrival visibility. [Input](../pseudocode/Input.pseudo) |
| Vehicle/package networks; arc tables and Eq. 17 | `RoadNetwork.cs` builds owner-specific layers and arc dictionaries through seven categories. These categories span several paper arc families. | All 13 vehicle and 15 package families, including transfer, unused and unserved arcs, with explicit endpoint conventions. [Network construction](../pseudocode/RoadNetwork.pseudo), [arc rules](../specs/NETWORK_RULES.md) |
| Arc objective, flow, coupling, capacity and duty; Eqs. 5–17 | `vrp_time_space.cs` supplies the direct Y/Z model. | Equation-level rows, objective weights, duty limits, service indicators and validated plan extraction. [Arc model](../pseudocode/ArcModel.pseudo) |
| Initial route pool | `Program.cs` calls `vrp_time_space_ini` and `vrp_time_space_vis_pas`; `A_B_generator.cs` consumes their solutions. The two initializer classes are absent from the source distribution. | Initialization interfaces, permitted unused/unserved routes and feasible service seeds. [CreateSeedPool](../pseudocode/ArcModel.pseudo) |
| Route coefficients and costs | `A_B_generator.cs` builds A/B, cost and route dictionaries. | Separate physical ownership and service incidence; one package choice for linked pickup/delivery fragments; ordered extraction, zero-cost routes and consistent coefficient views. [Column extraction](../pseudocode/A_B_generator.pseudo) |
| Nonlinear and linearized master; Eqs. 18–31 | `GeneratingMasterProblem.cs` and `GeneratingMasterProblemQ.cs` provide route-selection models. Their coverage, capacity activation and quadratic-variable domains differ from the paper. | Physical-vehicle ownership, all product inequalities, activated capacity and integer-pool validation. [Linearized master](../pseudocode/GeneratingMasterProblem.pseudo), [nonlinear master](../pseudocode/GeneratingMasterProblemQ.pseudo) |
| Vehicle pricing; Eqs. 32–36 | `SubProblemGeneratorVeh.cs` constructs vehicle pricing. Duty and branch constraints require separate treatment. | Per-vehicle path model, duty limits, inherited branches, route-indexed dual context and objective/status outputs. [Vehicle pricing](../pseudocode/SubProblemGeneratorVeh.pseudo) |
| Package pricing; Eqs. 37–40 | `SubProblemGeneratorPas.cs` constructs package paths, then solves for supporting vehicle routes using a second objective. | Separate pricing/support results, complete package paths and validated branch restrictions. [Package pricing](../pseudocode/SubProblemGeneratorPas.pseudo) |
| Column-generation loop | `GeneratingSubProblem.cs` and `Program.cs` coordinate the master and pricing. | Candidate admission, duplicate handling, solver statuses, resource limits and termination scope. [Pricing coordinator](../pseudocode/GeneratingSubProblem.pseudo), [controller](../pseudocode/Program.pseudo) |
| Integrality search | `ClassName/BB_info.cs`, `ClassName/BB_node.cs`, `Program.cs` and the master provide branch data and integrality checks. Vehicle restrictions do not reach future pricing in the C# path. | Stable branch keys, restrictions on existing and future columns, unresolved-node records and feasible-plan reconstruction. [Branching](../pseudocode/Branching.pseudo) |
| New-order assignment | `OrderManager.cs` supplies route-neighborhood screening. | Separate eligibility tests and optional heuristic restrictions; multimodal reachability from committed vehicle states. [Order assignment](../pseudocode/OrderManager.pseudo) |
| Committed execution and periodic replanning | `DynConstrGenerater.cs` and the dynamic loop in `Program.cs` supply update constraints and repeated solves. | Ongoing travel, onboard packages, accepted obligations, selected-plan handoff and retention of the previous plan after a failed update. [Commitments](../pseudocode/DynConstrGenerater.pseudo), [dynamic update](../pseudocode/DynamicUpdate.pseudo) |
| Plans, service metrics and experiments | `Program.cs` formatters and `Generating_TS_RS_results.cs` supply reports and case sweeps. Paper experiment inputs and result files are separate from this distribution. | Carrier reconstruction, plan validation and metrics tied to the corresponding case and model. [Results](../pseudocode/Results.pseudo), [batch interface](../pseudocode/BatchDrivers.pseudo) |

The [examples](../examples/README.md) exercise route feasibility and dynamic-order updates with synthetic inputs; [validation](../validation/RESULTS.md) records their expected and actual outputs.
